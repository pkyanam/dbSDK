## Is dbSDK an ORM?

No. There is no schema, no query builder, no migrations, no model
definitions. You write SQL; dbSDK handles binding, results, errors,
transactions, and capability checks. If you want a query builder or an
ORM, use one; your SQL stays yours.

## Does dbSDK host my database?

No. There is no dbSDK backend, no credential proxy, and no hosted
anything. On the management side, your provider credential goes from your
process straight to the provider's official API. On the query side, your
connection string goes straight to the database. dbSDK is a client library
and nothing else.

## Is this an admin panel?

No. There is no UI. The management layer gives your code (and your agents)
a typed verb set over provider resources; the provider's own console
remains the place to look at accounts, billing, and history. What dbSDK
adds is normalization, pre-dispatch capability checks, bounded waiting,
and honest error reporting around those API calls.

## Can I create databases with it?

Yes, where the provider has a management API: with a Neon API key or a
Supabase personal access token, the management client can create projects
(and Neon branches and databases), wait until they are ready, and hand
back connection details for the query client. See
[Management](/docs/management) and [Credentials](/docs/credentials). The
PostgreSQL connector is the exception by design: it connects to a server
you already have, and there is no provider API for it to call.

## Does my SQL run on any database?

Within the launch adapters, your SQL runs on PostgreSQL, on every adapter,
unchanged. dbSDK does not translate SQL between engines, and no future
engine family will be bridged by rewriting your queries. A wider set of
services would come with the same client conventions and their own query
dialects.

## Is it safe against SQL injection?

Parameterization is the default and the value path is closed: interpolated
values always become bind parameters. Dynamic identifiers are the one
thing values must never become, and they have a separate API
(`sql.identifier`) that validates and quotes segments. If you construct
SQL text with plain string concatenation, you are outside dbSDK's
protections; the library cannot stop you from using `db.query({ text })`
with hand-built strings.

## What happens when I call a feature a transport cannot do?

It fails before dispatch with `DbError` code `CAPABILITY`, naming the
capability. Nothing is sent to the network, nothing falls back to another
code path, and no error is invented after the fact. See
[Capabilities](/docs/capabilities).

## A write failed but might have committed. What now?

The error is marked `indeterminate`. dbSDK does not retry it and does not
tell you it failed definitively. Make the write idempotent (client
generated primary key, `on conflict` upsert) so a retry is safe, or verify
against the server before acting. See
[Transactions](/docs/transactions).

## Why no `live` evidence for hosted Supabase and Neon?

Because this project has not queried hosted instances of either service.
The test suite verifies behavior against a real local PostgreSQL and the
real Neon HTTP protocol through a local proxy, and the docs describe that
precisely. Evidence levels on the capabilities page say exactly what was
checked and how.

## Why does Supabase need a custom CA certificate?

Supabase's Postgres endpoints present certificates signed by Supabase's
own root CA, which is not in the Node trust store. dbSDK defaults to
certificate verification on, so first connections fail loudly unless you
supply that CA (from the Supabase dashboard) via `pool: { ssl: { ca } }`,
or explicitly opt out with `ssl: { rejectUnauthorized: false }`. This is a
deliberate tradeoff: encrypted-but-unverified TLS does not stop a
man-in-the-middle. Details in the
[Supabase adapter](/docs/adapters/supabase).

## Can I use it in the browser?

No. Connection strings are secrets and belong on a server. There is no
browser build. If you need database access from client code, put an API in
front of it.

## Can I use the Supabase Data API or RLS with the user's identity?

Not through this adapter. It speaks the PostgreSQL wire protocol as the
role in your connection string. Policies based on `auth.uid()` evaluate
without request context on a plain SQL connection. The PostgREST path is a
different surface, and dbSDK does not re-implement it. See the RLS section
of the [Supabase adapter](/docs/adapters/supabase) for the two patterns
that work.
